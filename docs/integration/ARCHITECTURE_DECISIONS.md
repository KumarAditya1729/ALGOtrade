# Architecture Decisions

This document captures the architectural decisions made for merging OpenAlgo and QuantDinger into a single, unified AI Trading Platform. Each conflict is evaluated based on correctness, security, reliability, testability, maintainability, scalability, and extensibility.

## 1. Canonical Backend
**Decision**: QuantDinger (Flask + Gunicorn + Celery + Dedicated Workers)
- **Why Retained**: Strict separation of HTTP web requests from long-lived trading and scheduler loops. It is scalable and prevents a blocking API call from delaying order execution.
- **Why Adapted**: OpenAlgo's extensive blueprints (like Flow, tools, action center) will be migrated as routed services into the Flask backend but must offload execution to the `trading-worker` or Celery.

## 2. Canonical Frontend
**Decision**: OpenAlgo (React 19, Vite, shadcn/ui)
- **Why Retained**: Provides a unified, monolithic SPA which already integrates Flow (visual strategy builder), Python IDE, and Options Tools.
- **Why Adapted**: QuantDinger lacks a unified frontend within its core repo (it uses separate repos). We will adapt OpenAlgo's React frontend to interface with QuantDinger's robust APIs (like Agent Gateway, backtesting) while maintaining the single pane of glass.

## 3. Canonical PostgreSQL/Data Layer
**Decision**: QuantDinger (PostgreSQL 18 + Redis 8)
- **Why Retained**: SQLite and threaded isolation are insufficient for a multi-worker, horizontally scalable deployment. PostgreSQL ensures ACID compliance for orders, leases, and multi-tenant isolation. Redis handles distributed locks, celery queues, and cache.
- **Why Replaced**: OpenAlgo's SQLite is replaced to prevent database lock contention. DuckDB might optionally be retained purely as a fast timeseries backend for historical market data if PostgreSQL partitioning is not enough.

## 4. Canonical Execution/Order Lifecycle
**Decision**: QuantDinger Trading-Worker Model
- **Why Retained**: It abstracts execution into a separate, highly-controlled `trading-worker` process. Order states, idempotency, and reconciliation are inherently safer when isolated from HTTP.
- **Why Replaced**: OpenAlgo's thread-based execution within the API process is discarded for stability reasons.
- **Constraint**: Strict `PAPER` and `LIVE` execution modes must be enforced at the worker level.

## 5. Canonical Broker Abstraction
**Decision**: OpenAlgo Broker Plugins + QuantDinger Adapter Interface
- **Why Retained**: OpenAlgo has 34 broker integrations (largely Indian markets), which is a massive functional asset.
- **Why Adapted**: OpenAlgo's plugins must be normalized to fit QuantDinger's internal `BrokerAdapter` contract (e.g. `place_order`, `get_positions`, `subscribe_market_data`). They will be instantiated and executed securely inside the `trading-worker`.
- **Note on Shims**: The `backend/app/services/live_trading/brokers/_shims/` directory serves strictly as a temporary migration boundary to prevent legacy SQLite dependencies from polluting the Celery worker process. The target architectural state must convert these plugins to standard QuantDinger native adapters that fetch credentials explicitly from a secure PostgreSQL Credential Service, rather than relying on `contextvars` and mock database files.

## 6. Market-Data Architecture
**Decision**: OpenAlgo ZeroMQ WebSocket Proxy (Adapted)
- **Why Retained**: OpenAlgo has a highly unified WebSocket implementation across its 34 brokers.
- **Why Adapted**: It will be decoupled into a dedicated `market-data-worker` (or integrated into `trading-worker`) that pushes state into Redis or directly to strategy runtimes, rather than running inside the main web process.

## 7. Strategy/Runtime Architecture
**Decision**: Hybrid (OpenAlgo Ideation + QuantDinger Execution)
- **Why Retained**: OpenAlgo's Flow (No-Code) and Browser Python Editor are kept for the ideation and strategy definition layer.
- **Why Adapted**: The strategies generated by Flow/Python Editor will not execute in a generic unmanaged thread. They will be serialized and dispatched to QuantDinger's `trading-worker` which manages the Strategy API V2 lifecycle (intents, scaling, position sizing, risk controls).

## 8. Backtesting Engine
**Decision**: QuantDinger Backtest Engine
- **Why Retained**: Dedicated, mature backtesting engine that simulates execution, fees, slippage, and outputs detailed metrics (Sharpe, drawdown). OpenAlgo's sandbox is a paper-trading clone, not a high-speed historical backtester.
- **Why Adapted**: Will be exposed to OpenAlgo's frontend UI and Flow builder.

## 9. AI/Agent/MCP Boundary
**Decision**: QuantDinger Agent Gateway and MCP
- **Why Retained**: QuantDinger provides strict rate-limiting, scopes, and token verification, separating paper/live trading for AI agents. OpenAlgo's MCP is too direct for a multi-tenant or secure deployment.
- **Why Adapted**: Tools from OpenAlgo (like Flow generation or specific broker queries) will be registered into QuantDinger's MCP server. Live trading authority remains explicitly guarded.

## 10. Redis/Queue/Worker Architecture
**Decision**: QuantDinger Celery + Redis
- **Why Retained**: Provides durable finite job execution (backtests, AI reports), retries, and task routing. Replaces OpenAlgo's background threads.

## 11. Observability
**Decision**: QuantDinger Prometheus + Grafana
- **Why Retained**: Industry standard, decoupled metrics scraping and dashboards. OpenAlgo's internal tracking (Traffic, Latency) will emit metrics to Prometheus instead of storing them in SQLite, reducing database bloat.

## 12. Authentication / Authorization
**Decision**: QuantDinger Model
- **Why Retained**: PostgreSQL-backed, Argon2 hashed, explicit administrator provisioning, and Fernet credential encryption. Prevents live trading by default and isolates tenant/user credentials securely.
